# knoter Daily Report Template

> Purpose: external LLM agents use this template with `kn_search` and `kn_get`
> results to generate a daily report from the user's notes. The backend should
> expose notes, chunks, metadata, and template text; the LLM agent writes the
> final prose.

---

## 1. Report Contract

### Document Layers

`knoter` documents are managed in three layers. Report generation should never
collapse these layers into one ambiguous document type.

1. Source
   - User-authored or user-collected raw material.
   - Examples: Markdown notes, scraped text, images, audio files, PDFs.
   - Moved into the vault's source directory and referenced by path.
   - Managed by day in the project/vault.
   - Preserved as evidence and audit trail; not optimized for chunking.
   - Not chunked or embedded by default.
2. Rewritten Source
   - External LLM agent rewrites the source for retrieval.
   - This layer normalizes structure, headings, timestamps, OCR/transcription
     output, task markers, and workout metrics.
   - This is the primary document layer for chunking, indexing, and retrieval.
   - Must retain links back to source ids/paths and transformation metadata.
3. Final Artifact
   - User-visible output generated by an external LLM agent.
   - Examples: daily report, todo list, workout graph data, llm-wiki page,
     project status report.
   - Created by combining retrieved rewritten sources with a user-selected
     template.
   - Should be stored separately from source and rewritten source documents.
   - Chunked and embedded, but excluded from default search to prevent report
     self-reference loops. Include only with an explicit option.

Recommended path model:

```text
sources/YYYY-MM-DD/...
rewritten/YYYY-MM-DD/...
artifacts/YYYY-MM-DD/daily-report.md
artifacts/YYYY-MM-DD/todo.md
.kn/template.md
```

### Inputs

The agent should receive a structured bundle with:

- `date`: target local date, e.g. `2026-05-08`
- `timezone`: user timezone, e.g. `Asia/Seoul`
- `templateVersion`: template identifier
- `documentLayer`: usually `rewritten`
- `vaultStatus`: note/chunk/tag/index status
- `dailyNotes`: notes dated on the target date
- `tasks`: extracted task/todo candidates
- `areas`: grouped notes by user interest area
- `workouts`: exercise logs and inferred counts
- `retrieval`: search results with source path, chunk id, score, heading, tags
- `userPreferences`: optional tone, report length, excluded topics

### Output

The final report must be Markdown and must preserve source traceability:

- Every concrete claim should be grounded in a note path or chunk id if possible.
- Uncertain inferences must be labeled as inference, not fact.
- Missing data should be called out briefly instead of hallucinated.
- Private, sensitive, or emotionally heavy entries should be summarized with care.

## 2. Data Collection Plan

Run retrieval in this order:

1. Source inventory:
   - Query or list raw source entries for the target date.
   - Goal: verify what evidence exists before relying on generated documents.
2. Rewritten-source retrieval:
   - Query rewritten documents first because they are optimized for chunking.
   - Goal: use stable headings, normalized task markers, and extracted metrics.
3. Target-date exact retrieval:
   - Query: target date in `YYYY-MM-DD`, local date aliases, and daily-note path patterns.
   - Goal: find the user's main daily note.
4. Task/todo retrieval:
   - Query examples: `task todo 할 일 해야 할 것 완료 미완료 [ ] [x]`
   - Goal: collect open tasks, completed tasks, deferred tasks.
5. Area retrieval:
   - Query each known interest area: `llm-wiki`, `tasks`, `todo`, `운동`, project names, current tags.
   - Goal: group activity by subject instead of by file only.
6. Workout retrieval:
   - Query examples: `운동 헬스 러닝 걷기 스쿼트 푸시업 횟수 세트 km kg`
   - Goal: count exercise type, volume, streak signals.
7. Recent continuity retrieval:
   - Query yesterday and the previous 7 days for unresolved tasks and recurring routines.
   - Goal: make the report useful, not just a same-day summary.

Recommended search options:

```json
{
  "mode": "hybrid",
  "top": 20,
  "lang": "ko",
  "semanticMin": 0.2,
  "hybridMin": 0.25
}
```

## 3. Parsing Rules

### Daily Notes

Treat a note as a daily note when any of these match:

- `frontmatter.date` equals target date
- file name contains target date, e.g. `2026-05-08.md`
- title contains target date or common daily-note labels
- tags contain `daily`, `journal`, `일일`, `데일리`

### Tasks And Todos

Recognize Markdown task markers and natural-language todo expressions:

```markdown
- [ ] open task
- [x] completed task
- TODO: something
- 할 일: something
- 해야 함: something
```

Task status mapping:

- `done`: checked task, completed wording, or explicit completion timestamp
- `open`: unchecked task or future action wording
- `deferred`: postponed wording, blocked wording, or moved date
- `unknown`: task-like sentence without enough status evidence

### Workouts

Extract:

- `exerciseType`: e.g. walking, running, weights, push-up, squat, stretching
- `count`: repetitions or sessions
- `sets`: number of sets
- `durationMinutes`: duration if present
- `distanceKm`: distance if present
- `weightKg`: load if present
- `intensity`: low, medium, high, unknown

If the workout was mentioned but no count exists, report it as qualitative only.

### Interest Areas

Group notes by user-interest unit:

- `llm-wiki`: wiki generation, knowledge structuring, long-form synthesis
- `tasks`: task management mechanics, issue lists, project execution
- `todo`: personal todo entries and short next actions
- `daily-workout-graph`: exercise counts, streaks, graphable metrics
- `knoter`: backend CLI, MCP, search, chunking, template/report automation
- `other`: items that do not fit a known area

The implementation should allow users to configure these groups later in
`vault.json` or a front-end settings panel.

## 4. Report Markdown

Use this output shape:

~~~markdown
# Daily Report: {{date}}

## Summary
- {{one_sentence_overview}}
- {{most_important_progress}}
- {{main_risk_or_blocker}}

## Today Done
- {{completed_item}} (source: {{path_or_chunk}})

## Open Tasks
- [ ] {{open_task}} (source: {{path_or_chunk}})

## Deferred Or Blocked
- {{blocked_item}} - {{reason_if_known}} (source: {{path_or_chunk}})

## Area Notes
### {{area_name}}
- {{area_summary}}
- Evidence: {{path_or_chunk}}

## Workout
- Sessions: {{session_count_or_unknown}}
- Types: {{exercise_types}}
- Volume: {{counts_sets_distance_duration}}
- Graph data candidate:
  ```json
  {{workout_metric_json}}
  ```

## Useful Suggestions
- {{actionable_suggestion_based_on_notes}}
- {{small_next_step}}

## Sources
- {{path}}#{{chunk_id}} - {{brief_reason}}
~~~

## 5. Agent Instructions

System instruction:

```text
You generate a daily report from the user's local notes. Use only supplied
sources. Be concise, concrete, and useful. Do not invent tasks, workout counts,
or emotional interpretation. If evidence is weak, say "추정" or "근거 부족".
Prefer Korean unless the user's note is mostly another language.
```

User prompt skeleton:

```text
대상 날짜: {{date}}
타임존: {{timezone}}

아래 knoter 검색/조회 결과와 템플릿을 사용해 일일 보고서를 작성하라.
중요한 목표:
- 오늘 한 일과 미완료 작업을 분리한다.
- 분야별로 묶어 사용자가 다음 행동을 정하기 쉽게 한다.
- 운동 기록은 그래프 데이터로 재사용 가능하게 JSON 후보를 포함한다.
- 근거가 없는 내용은 생성하지 않는다.

템플릿:
{{template_text}}

검색/조회 결과:
{{retrieval_bundle}}
```

## 6. Backend Requirements

Minimum backend support needed before front-end work:

- Template file discovery: one vault-local `.kn/template.md`.
- Template validation: required sections and variables are present.
- Report context generation: date-scoped retrieval bundle without calling an LLM.
- MCP exposure: external agent can fetch template and context through tools.
- Metadata support: document date, document layer, note kind, source path,
  language, tags, chunk links.
- Source lineage: rewritten source and final artifact must point back to source
  ids/paths.
- CJK-safe retrieval: `Intl.Segmenter` chunking plus FTS5 trigram or bound preprocessor.
- LLM-free CLI: non-embedding commands return JSON/context only. Commands that
  require LLM calls belong under a future explicit `kn llm` namespace.
- Optional vectorless retrieval backend: PageIndex can be evaluated for
  reasoning-based retrieval over rewritten sources or long source documents.

Recommended CLI surface:

```bash
kn template list
kn template get daily-report
kn report context --date 2026-05-08 --template daily-report --format json
kn report context --date 2026-05-08 --layer rewritten --template daily-report --format json
```

Recommended MCP tools:

- `kn_template_get`
- `kn_report_context`
- `kn_get_batch`

## 7. Retrieval Backend Options

### Default: zvec + SQLite FTS5

Use this for short/medium rewritten Markdown documents and daily operational
search:

- dense semantic retrieval via zvec
- keyword retrieval via SQLite FTS5
- CJK-aware chunking and optional preprocessor
- good fit for tasks, todos, daily notes, workout metrics, and project notes
- excludes `artifact` by default; use explicit include option when needed

### CJK Keyword Strategy

Use a two-stage strategy:

- Baseline: SQLite FTS5 `trigram` for CJK substring matching with no external
  runtime dependency.
- Upgrade path: vault-local morphological preprocessor for Korean/Japanese
  rewritten/artifact content.

Recommended preprocessor direction:

- Korean/Japanese: Lindera or MeCab-compatible tokenizer.
- Chinese: evaluate Jieba-style segmentation separately.
- Fallback: `Intl.Segmenter` word segmentation when no external preprocessor is
  available.

### Optional: PageIndex

PageIndex is a vectorless, reasoning-based RAG approach that builds a
hierarchical tree index and lets an LLM navigate that tree instead of retrieving
by vector similarity.

Reference: https://github.com/VectifyAI/PageIndex

Potential use in `knoter`:

- long PDFs, scraped reports, books, and large source documents
- rewritten sources with clear headings and hierarchy
- workflows where explainability and section traceability matter more than fast
  approximate search
- image/PDF-heavy sources after OCR or vision-based conversion

Do not replace zvec by default. Treat PageIndex as a pluggable retrieval backend:

```json
{
  "retrieval": {
    "backend": "hybrid",
    "alternatives": ["pageindex"],
    "pageindex": {
      "enabled": false,
      "scope": ["source", "rewritten"],
      "indexPath": ".kn/pageindex"
    }
  }
}
```

Recommended decision rule:

- Use `hybrid` for daily notes, tasks, todos, short project logs, and graphable
  records.
- Use `pageindex` for long, structured, professional, or multimedia-derived
  documents where tree navigation is more useful than chunk similarity.
