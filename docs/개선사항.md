## P1. Podman rootless IPv6 바인딩 불일치 (수정 완료)

**증상**
`podman run -p 8080:80` 시 호스트 0.0.0.0:8080 LISTEN 되지만 IPv4 전용 바인딩.
클라이언트가 `localhost` → IPv6 `::1`로 먼저 해석하면 TCP 핸드셰이크는 성립하되
즉시 `Recv failure: 상대편이 연결을 끊음` 발생. Bun/fetch, curl 모두 재현.

**원인**
podman rootless 네트워크 모드(pasta/slirp4netns)가 IPv4만 바인딩. 시스템에 IPv6 loopback이
있으면 `localhost` 해석이 IPv6 우선.

**수정**
- `src/commands/vault.ts`: `embedding.baseUrl` 기본값 `http://localhost:<port>` → `http://127.0.0.1:<port>`
- 이미 생성된 vault는 `.kn/vault.json`의 `baseUrl`을 수동으로 `127.0.0.1`로 교체

**향후 대안**
- `podman run --network slirp4netns:enable_ipv6=true ...`로 컨테이너 측 IPv6 바인딩 추가
- 또는 `fetch` 단에서 DNS 해석 후 IPv4 우선 재시도 로직

## P2. Semantic score 방향이 역직관적

**증상**
`kn search "연극" --mode semantic` 결과에서 실제 관련 매치(극단이 포함된 꿈.md)가
score 0.65로 1위, 무관 매치(자료구조.md)가 score 0.88로 하위에 노출.

**원인**
zvec COSINE metric은 **거리(distance)** 반환 (0에 가까울수록 유사). 현재 코드는
이 값을 그대로 `score`로 envelope에 실음 → 사용자 관점에서 "점수가 높으면 좋다"는
관습 반대.

**개선안**
두 가지 중 택1:
1. **정규화**: `semantic_score = 1 - min(distance, 1)`로 변환해 envelope에 노출.
   정렬 로직도 descending으로 통일.
2. **필드 분리**: `distance` 필드를 그대로 두되 `score` 필드는 1-distance로 채우고
   문서에 명시.

**영향 범위**
- `src/stores/vec-store.ts::toSearchResult`
- `src/search/fusion.ts::linearFusion` — 퓨전 전 정규화 필요 (BM25는 이미 0~1 정규화됨)
- `src/search/hybrid.ts::keywordSearch` 응답 필드 일관성

**주의**
`strongSignal` / `--semantic-min` / `--hybrid-min` 임계값 해석이 반대로 뒤집히므로
기존 값 재튜닝 필요.

## P3. FTS5 한글 키워드 검색 실패

**증상**
`kn search "캡디" --mode keyword` → 0 hit. 실제로는 "캡디llm.md" 파일 본문에 여러 번
등장. `search "살인사건" --mode keyword`도 hit 0.

**원인**
SQLite FTS5 기본 토크나이저(`unicode61`)는 공백/구두점 기반 분할만 수행. 한글은 공백
없이 단어가 연결되는 경우가 많아 토큰이 문서 전체 한 덩어리로 잡힘. CJK 일반 문제.

**개선안 (우선순위 순)**
1. **`trigram` 토크나이저로 전환** — SQLite 3.34+ 내장. CJK 부분 매칭 가능.
   `CREATE VIRTUAL TABLE chunks_fts USING fts5(..., tokenize='trigram')`로 대체.
   쿼리 측도 trigram 인덱스에 맞춰 재작성 필요.
2. **외부 preprocessor 바인딩** — `src/pipeline/preprocessor.ts`에 기반 구조는 이미
   있으나 인덱스측 적용이 미완. 한글 형태소 분석기(mecab-ko 등)를 stdin/stdout
   프로토콜로 연결 후 FTS5 `content=` 재빌드.
3. **Intl.Segmenter 기반 자체 토크나이저** — `Intl.Segmenter('ko', { granularity: 'word' })`
   출력을 공백 조인으로 치환하여 FTS5에 저장. 외부 바이너리 의존성 없음.

**단기 권장**: 1번 (`trigram`) — 변경 폭 작고 효과 즉시 확인 가능.

## P4. 날짜 필터가 인덱싱 시각 기준

**증상**
`kn search --after 2026-04-01` → `createdAt: "2026-04-23..."` (전부 오늘 인덱싱된 값)
노트 자체의 논리적 날짜(파일명 `2026-04-05.md`나 frontmatter `date:`)가 아닌
DB에 insert된 시각만 반영.

**원인**
`MetaDB.insertNote`가 `created_at = ISO now()`로 덮어씀. 파일 mtime이나 frontmatter의
날짜를 반영하는 경로 없음.

**개선안**
- `notes` 스키마에 `file_mtime` / `doc_date` 컬럼 분리 추가
- 파서가 frontmatter `date:` / `created:` 인식 → 없으면 `statSync(filePath).mtime`
  사용
- `--after` / `--before` 필터를 `doc_date` 우선, 없으면 `file_mtime`, 그것도 없으면
  `created_at`으로 폴백

**마이그레이션**
ALTER TABLE 추가 + 기존 노트 재인덱싱 시 채움. 비파괴적.

## P5. TEI readiness 타임아웃이 대용량 모델에 부족

**증상**
현재 `waitForReady(url, 30000)` 기본 30초. dragonkue 모델 첫 로드 시 weights 다운로드
(~1.4GB) + candle 로드 + warmup으로 수 분 소요. lazy-start 경로에선 30초 내 준비
실패하고 경고 후 재호출에서 빠르게 성공하지만, UX상 혼란.

**개선안**
- 기본 타임아웃 상향 (120s~300s) 또는
- `VaultConfig.embedding.container.readyTimeoutMs` 설정 필드 추가
- 또는 **첫 기동 감지** 휴리스틱: `podman start` 반환 시점 직후라면 긴 타임아웃, 이후엔 짧은
  타임아웃

## P7. 에러 메시지 개선

현재 TEI 연결 실패 시 `OpenAI embedding failed: The socket connection was closed
unexpectedly` 식 중복 출력 + 원인 불명확. 사용자가 P1 같은 네트워크 문제를 진단하기
어려움.

**개선안**
- `fetchWithContainerRetry`에서 ECONNREFUSED / ECONNRESET / "socket closed"를
  각각 분류해 힌트 문구 첨부 (e.g., "container may be bound to IPv4 only; try
  http://127.0.0.1:<port>")
- 재시도 실패 시 한 번만 최종 에러 출력 (청크 수만큼 반복 출력 방지)
